## Settings page

| Section | Editable product settings | Design requirement |
| --- | --- | --- |
| Instance | Display name, shared/personal operation, address tone | Explain the effect of a mode change and preserve existing data |
| Subjects and courses | Profiles, levels, terminology, metadata, course membership | Preview the resulting upload fields and learner labels |
| Sharing and review | Default audiences and designated reviewers | Defaults never expand existing sources' access silently |
| Materials | Enabled formats, size/duration limits within operator bounds | Explain unavailable processing capabilities |
| Learning | Available activities, default question scope, objectives | Separate source explanation from activity generation |
| Processing and storage | Permitted provider choices, job limits, retention | Show operator-enforced limits and current availability |

## Backend

- [ ] Persist typed settings with validation, a configuration revision and an audit entry for
  sensitive changes. Use stable identifiers for catalog entries. Archive used entries instead
  of deleting data they still identify.
- [ ] Define precedence: deployment restrictions, instance choices, subject/course specialisation.
  Course choices can narrow access and capabilities, never bypass deployment restrictions.
- [ ] Make server and worker observe committed settings consistently. Jobs capture the applicable
  configuration revision and recheck permissions when executed. Flag stale drafts after relevant
  policy or source changes.
- [ ] Keep secrets, filesystem locations and unrestricted provider URLs in operator configuration.
  The UI can show availability or choose among configured services, without returning secrets.
- [ ] Save related settings atomically. Detect concurrent edits, preserve entered values on
  validation errors, and show the consequence before a change requiring reindexing or migration.
- [ ] Require an explicit action for destructive retention changes or operating-mode transitions.
  Prevent personal mode from silently collapsing an instance containing multiple users.

## Frontend and design

Use a normal settings page with section navigation and section-level Save/Cancel. Avoid a long
wizard for routine changes. Place settings in the account/administration area rather than adding
several primary navigation entries. Provide a preview, unsaved-change handling, inline validation,
read-only states and clear saved/error feedback.

## Acceptance

- [ ] An authorised administrator adds a subject and adjusts its fields without editing files.
- [ ] A worker running during a configuration change uses a coherent revision.
- [ ] Invalid settings and stale edits preserve user input and do not partially save.
- [ ] Network responses and configuration exports contain no credentials.
- [ ] Changing labels leaves existing citations, identifiers and access intact.
